# GridPulse — Product Requirements Document

**Status:** Planning  
**Project type:** B.Tech Machine Learning project  
**Product category:** Building energy analytics  
**Owner:** GridPulse project team

## 1. Product summary

GridPulse is a machine-learning application that analyses historical household electricity consumption, forecasts the next 24 hours of average demand, identifies unusual usage patterns, and explains its outputs through an interactive dashboard.

The MVP is an offline-data-driven prototype based on a public, historical single-household dataset. It is **not** a live utility-grid monitor, an IoT deployment, or a system that can prove energy waste.

## 2. Problem statement

Electricity readings are difficult to interpret as raw time-series data. Users need a concise view of expected consumption, changes from historical patterns, and whether a forecast is reliable enough to be useful. GridPulse will turn historical readings into transparent forecasts and anomaly signals, with model performance visible rather than hidden behind a single accuracy number.

## 3. Goals

1. Ingest and validate the selected public electricity dataset reproducibly.
2. Aggregate minute-level active-power readings into hourly observations.
3. Forecast the next 24 hourly observations using a tested ML pipeline.
4. Detect potentially unusual consumption using a defined, validated baseline.
5. Compare ML models with simple forecasting baselines using chronological evaluation.
6. Present forecasts, anomalies, data quality and evaluation metrics in a clear responsive dashboard.
7. Make the system reproducible through documented setup, tests and model-training commands.

## 4. Non-goals for the first release

- Direct connection to smart meters, live utility systems or IoT hardware.
- Claims of generalisation to all buildings or to grid-wide electricity demand.
- Automatic control of electrical equipment or energy billing.
- Guaranteed savings or definitive claims that an anomaly is wasted energy.
- User accounts, payments, complex microservices, or an LLM chatbot.
- Weather-aware forecasting from the primary dataset, which does not provide weather features.

## 5. Target users

- Students and evaluators reviewing an end-to-end ML project.
- Building or household users exploring historical consumption patterns.
- Developers interested in interpretable forecasting and model evaluation.

## 6. MVP user journeys

1. **Overview:** inspect the available date range, recent consumption, next-24-hour forecast summary and latest anomaly signals.
2. **Forecast:** explore historical actuals versus predicted values, select a historical window, and review model error metrics.
3. **Anomaly intelligence:** inspect unusual time periods, observed value, expected baseline, deviation and the rule that triggered the alert.
4. **Model lab:** compare the baseline and candidate algorithms on the same chronological evaluation windows.
5. **Dataset health:** review row counts, time coverage, missing readings, aggregation coverage and validation warnings.

## 7. Functional requirements

- **FR-01 Data ingestion:** read the UCI source file from a local path; never require the raw dataset to be committed to Git.
- **FR-02 Validation:** parse dates and numeric fields; recognise missing-value markers; report duplicate timestamps, gaps, missingness and invalid values.
- **FR-03 Aggregation:** create hourly average active-power observations and exclude hours below a configurable coverage threshold.
- **FR-04 Forecasting:** provide a next-24-hour forecast generated by the selected, evaluated model.
- **FR-05 Baselines:** evaluate persistence and 24-hour seasonal-naive baselines before claiming value from more complex models.
- **FR-06 Anomaly detection:** flag statistically unusual deviations from expected consumption using thresholds calibrated on validation data.
- **FR-07 Explainability:** show measured deviation and relevant historical context; display global feature importance where supported.
- **FR-08 Evaluation:** expose MAE and RMSE, with forecast strategy, evaluation period and units clearly stated.
- **FR-09 API:** serve typed health, overview, forecast, anomaly, dataset-health and model-metric responses.
- **FR-10 User experience:** handle loading, empty, invalid-data and API-error states without fabricated values.

## 8. Non-functional requirements

- Reproducible preprocessing and model training with fixed random seeds where relevant.
- Chronological train/validation/test separation to prevent time leakage.
- Clear units, timestamps, data provenance and visible limitations.
- No secrets, virtual environments, raw datasets or generated model artefacts committed to Git.
- Automated tests for data parsing, feature generation, split ordering, forecast shape and API contracts.
- Responsive UI and accessible labels/contrast.
- Model metrics must come from actual evaluation runs; do not hard-code or invent results.

## 9. Definition of done for the MVP

The MVP is ready for demonstration when a documented dataset can be processed from raw file to hourly series, candidate models can be evaluated against baselines on time-ordered holdout data, a forecast and anomaly results can be served through the API, the dashboard displays real backend outputs, automated tests pass, and the README explains setup, data attribution, evaluation and limitations.

## 10. Success measures

We will report, rather than pre-claim, the following:
- MAE and RMSE versus each simple baseline on the same held-out forecast origins.
- Results across multiple 24-hour forecast origins, not only a single hand-picked example.
- Data quality counts and number of valid hourly observations.
- Anomaly review examples showing actual value, expected value, deviation and threshold.
- Test results, reproducibility instructions and application response health.

## 11. Current decisions

- Primary dataset: UCI Individual Household Electric Power Consumption.
- Target: hourly mean of `Global_active_power`, in kW.
- Forecast horizon: next 24 hourly points.
- Initial models: persistence, seasonal-naive, Linear Regression, Random Forest and HistGradientBoostingRegressor.
- Frontend: React/Next.js with TypeScript and a utility-first styling system, subject to the approved UI design.
- Backend: Python + FastAPI.
- ML: Pandas, NumPy and scikit-learn; MLflow can be added after a working baseline exists.
- Dataset files and trained artefacts remain local or in appropriate external storage, not in the Git repository.
